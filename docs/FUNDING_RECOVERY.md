# История funding и восстановление 0.12

Архив истории загружается отдельной командой, без ключей и сделок. Частый сбор стаканов
и текущая экономика продолжают использовать свой независимый 48-часовой кэш; загрузка
30 дней не добавляется в каждый цикл. Базовый реестр — 10 активов / 60 контрактов.

```powershell
# Импорт 31 дня с запасом на левую границу окон 7/30 дней
.\.venv\Scripts\python.exe -m arbitrage.funding_history --database data\funding-history.sqlite3
# Только выбранные зарегистрированные активы и биржи
.\.venv\Scripts\python.exe -m arbitrage.funding_history --database data\funding-history.sqlite3 --assets BTC ETH --exchanges binanceusdm bybit
# Прочитать сохранённые окна без сети
.\.venv\Scripts\python.exe -m arbitrage.funding_history --database data\funding-history.sqlite3 --read-only
```

В `funding_history_events` сохраняются биржа, нативный контракт, исходная метка события,
актив, дробная ставка и время наблюдения. Первичный ключ исключает повторные события;
новое значение опубликованной ставки обновляет запись. Отдельного журнала исправлений пока нет.
`funding_history_imports` хранит время последнего запроса и его ошибки. Повторный импорт
не очищает старые события. Ошибка нового импорта помечает покрытие неполным, даже если
часть истории уже находится в кэше. Команда read-only пересчитывает окна из сохранённых
событий на момент последнего импорта, а не выдаёт старые данные за текущие.

Запрос ограничен 12 страницами по 100 записей на контракт, 25 секундами на страницу;
встроенный rate limiter CCXT сохраняется. Используются временные курсоры Binance/Bybit/Gate/OKX
и номера страниц Bitget/MEXC. Курсор без продвижения, конфликт ставок, чужой инструмент,
неизвестная ставка, ошибка API или исчерпание лимита отмечаются явной ошибкой, не нулём.
Частично полученные данные сохраняются. После ошибки каталога соответствующие контракты
получают неполный импорт, а прежние события сохраняются.

Окно включает события `(end - days, end]`. Для `regular_observed_coverage` требуются
событие на левой границе или раньше, свежий правый край и единый наблюдаемый интервал
от минуты до суток. Допуск отклонения интервала — 1000 мс; исходные метки не округляются
и не изменяются. Пропуск полного периода или смена частоты даёт `partial_or_irregular`.
Это консервативная проверка наблюдаемых границ/ритма, не независимая гарантия всех записей API:
например, систематическое отсутствие каждого второго события без сведений о расписании
не всегда можно обнаружить. У недавно запущенного контракта полный период также не заявляется.

Средняя/min/max ставки — исторические дробные ставки, не денежные выплаты аккаунта,
не PnL и не прогноз. Архив не меняет будущие ставки в модели условного схождения.
Текущее подтверждение требует свежих funding и стаканов независимо от существования архива.
Готовый проверочный архив: `data/funding-history-check.sqlite3`, отчёт: `data/funding-history-check.json`.
В 0.13 добавлены фоновое обновление по расписанию и срок хранения funding:
[AUTOCARE.md](AUTOCARE.md). Отдельная команда остаётся доступна для ручного импорта.

## Восстановление после прерывания

Основной монитор удерживает блокировку `<database>.monitor.lock` на весь запуск.
Второй монитор для той же базы отказывается запускаться. Файл блокировки остаётся,
но блокировку держит ОС: она снимается при закрытии дескриптора или смерти процесса.
Наличие файла само по себе не означает активную сессию; удалять его для запуска не нужно.
Блокировка защищает запуски monitor, не произвольные внешние SQL-инструменты.

Новый процесс не загружает прежние подтверждения в память. В первой транзакции нового
запуска оставшиеся без ended эпизоды прежних сессий получают завершение с причиной
`previous_session_interrupted`. Старый запуск помечается `interrupted`, для него добавляется
терминальный снимок без текущих строк; это работает и с базами до таблицы `monitor_runs`.
Событие записывается один раз, в одной транзакции с первой новой публикацией.
В JSON нового запуска список таких событий доступен в `signals.recovered_events`.

Время recovery-события — время обнаружения новым запуском. Реальный момент аварии
неизвестен (`termination_time_known=false`); время последнего известного события сохранено
отдельно. При обычной остановке recovery не добавляется. Старый подтверждённый сценарий
не восстанавливается: текущие данные загружаются заново, счётчик начинается с нуля.
Подтверждения по-прежнему относятся к условной оценке, а не исполнению сделки.

После аварии старый JSON остаётся историческим файлом до первой новой публикации;
его возраст нужно учитывать. Очищать закрытые recovery-эпизоды разрешит обычная политика
срока хранения: если эпизод пересекает границу, подробная история пока защищена.
Операции paper trading и реальные позиции не восстанавливаются: они ещё не реализованы.
