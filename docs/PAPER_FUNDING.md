# Сверка funding для Paper Trading 0.23

Команда читает архив `funding_history_events` / `funding_history_imports` из рыночной
SQLite в режиме read-only. Forecast-ставки из economics не используются. Результат
и исходные ставки/цены сохраняются атомарно в отдельном paper-журнале, событие
аудита — `funding_reconciled`. Базы обязательно разные.

```powershell
Set-Location G:\Arbitrage
# Сверить ставки; без settlement mark prices это только оценка по входному номиналу
.\.venv\Scripts\python.exe -m arbitrage.paper funding --position "POSITION_ID" --market-database data/market.sqlite3
# Сверить с предоставленными ценами mark в моменты начислений
.\.venv\Scripts\python.exe -m arbitrage.paper funding --position "POSITION_ID" --market-database data/market.sqlite3 --funding-prices data/settlement-marks.json
```

Для replay-журнала добавьте `--replay --database data/replay-paper.sqlite3`.
Снимок latest.json этой команде не требуется. Она работает как для открытой, так
и для закрытой позиции; конечное время — последняя успешная переоценка/закрытие,
а не текущее время запуска команды. Событие точно в момент входа исключается,
точно в момент конечной оценки включается. Это явное соглашение модели для
граничных моментов, реальный порядок исполнения и funding счёта оно не подтверждает.

## Цены в момент начисления

Текущий архив хранит ставки, но не settlement mark price. Подстановка сегодняшней
цены или прогнозного midpoint дала бы неверное начисление. Поэтому файл цен
задаётся отдельно, пример структуры:

```json
[
  {
    "exchange": "binanceusdm",
    "native_id": "BTCUSDT",
    "timestamp_ms": 1700000000000,
    "mark_price_native": "100",
    "source": "ARTIFICIAL EXAMPLE ONLY; replace with actual price evidence"
  }
]
```

Пример искусственный. Нужны точные exchange/native_id/время события из отчёта
`missing_mark_prices`. Цена положительная и конечная, в USDT за нативную единицу
контракта: для `1000TOKEN` делится на реестровые `price_units=1000`.
Источник обязателен. Конфликтующие дубликаты отклоняются, одинаковые допускаются.
Файл пользователя не проходит независимую проверку происхождения:
`price_evidence_verified=false`; в 0.26 доступна точная загрузка Binance через --fetch-prices; другие адаптеры пока отсутствуют.

Расчёт каждой выплаты симуляции:

`LONG: −Q × mark_price_per_base × settled_rate`

`SHORT: +Q × mark_price_per_base × settled_rate`.

Отрицательная ставка меняет знак автоматически. Суммируются события обеих бирж
с их собственными временами; фиксированного общего количества выплат нет.

## Покрытие истории

Для каждой ноги необходимы три наблюдаемых события слева от/на времени входа,
одинаковый интервал всех соседних событий в контексте (1 минута — 24 часа),
отсутствие пропущенного ожидаемого события до конца окна, успешный импорт не
раньше конечного времени и совпадение инструмента/актива. Времена событий и
наблюдения не могут быть будущими относительно запуска (допуск 1с).
События после конца окна не начисляются. Максимум 2000 событий на ногу;
превышение означает неполное покрытие, не усечённый «полный» результат.

Это строгая проверка **наблюдаемого регулярного ритма**, а не доказательство
полноты биржевого API. Смена интервала, пропуск или недостаток контекста дают
partial, даже если часть ставок доступна. Известные валидные события остаются
в отчёте, но итог funding и net не заполняются. Если покрытие подтвердило,
что внутри окна выплат ещё не было, корректный результат равен нулю.

Статусы:

| Статус | Смысл |
|---|---|
| partial_history | История/импорт не покрывают обе ноги; итог null |
| rates_covered_marks_missing | Ставки покрыты, недостаёт цен; итог null |
| covered_paper_cashflows | Ставки и предоставленные цены полны; доступен итог симуляции |

`observed_priced_cashflow_usdt` — сумма только известных событий с ценами;
`observed_entry_notional_estimate_usdt` — сумма известных ставок по входному
номиналу. Это частичные суммы, не общий результат.
`entry_notional_estimate_usdt` и `net_entry_notional_estimate_usdt` выдаются только
при полном покрытии ставок и явно используют постоянную входную цену.
Они не заменяют settlement-mark расчёт и итоговый `net_pnl_usdt`.

## Повторы, изменения и отчёт

Сверка каждый раз пересчитывает всё окно из согласованного read-only снимка БД.
Повтор того же набора доказательств возвращает сохранённый результат, без нового
события и двойного начисления. Исправленная ставка/цена или изменившееся покрытие
создаёт новую запись аудита и заменяет итог. При ухудшении покрытия старый полный
итог очищается до null; неизвестное не становится нулём. Ошибка чтения/записи
откатывает операцию, предыдущий сохранённый результат остаётся последним известным.
В funding есть `reconciled_at_ms` и времена наблюдения/импорта.

Новая переоценка/закрытие сбрасывает funding: его нужно сверить для нового конца
окна. Повтор прежней mark-команды сохраняет уже сверенный результат.
`status` не перечитывает архив автоматически. Он суммирует итог только закрытых
позиций; общий net доступен, если funding покрыт у всех закрытых позиций.
Число таких позиций — `funding_covered_closed_count`; открытые в итог не входят.

Пока остаются ручные цены, сбор стаканов открытых позиций, автоматический цикл,
UI и живой прогон. Ни исполнение, ни фактические выплаты счёта не подтверждены.

```powershell
.\.venv\Scripts\python.exe validate_paper_funding.py --output data/paper-funding-check-2
```
