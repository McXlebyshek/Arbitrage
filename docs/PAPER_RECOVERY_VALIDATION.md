# Совместная проверка paper-процессов и восстановления

`validate_paper_recovery.py` проверяет rules, mark, funding и UI как отдельные
процессы на искусственных данных. Положительный вход создаёт сам rules-процесс;
готовая позиция в SQLite не подставляется. Цены, подтверждения, ставки и settlement
marks искусственные. Live-проверки возраста работают по текущим часам; режим
журнала `live_snapshot` здесь не означает происхождение данных с биржи.

```powershell
Set-Location G:\Arbitrage
.\.venv\Scripts\python.exe validate_paper_recovery.py --output data/paper-recovery-001 --port 8777
```

Папка должна быть новой, порт — свободным. Стенд откажется перезаписывать папку
или занимать используемый порт. По умолчанию запуск длится 95с, `--duration`
разрешает 95–300с. Процессы без окон, UI только на loopback. Биржевых запросов,
реальных ордеров и внешних уведомлений нет. Пользовательские базы и процессы
не изменяются; в `finally` завершаются только созданные дочерние процессы.

| Время от старта | Проверка |
|---|---|
| 0–8с | Вход по искусственному confirmed, одновременная переоценка и HTTP-чтение |
| 8–14с | Публикации без глубины: позиция остаётся открытой |
| 14–22с | Публикации прекращены: stale блокирует правила, UI снимает свежесть оценки |
| 22–28с | Источник помечен stopped, автоматические операции заблокированы |
| Около 28с | Принудительное завершение и повторный запуск rules/mark/funding; UI продолжает работать |
| После перезапуска | Новый конфиг take-profit=999, у позиции остаётся сохранённое значение 5 |
| После 48с | Искусственное схождение цен, закрытие по первоначальному take-profit |
| Около 88с | Плановый проход funding через 60с после перезапуска, сверка закрытой позиции |

Принудительное завершение проверяет восстановление после остановки процесса,
но не отключение питания или повреждение диска. Данные публикуются атомарно
обычным helper с ограниченными повторами Windows. Искусственный funding имеет
ритм 60с, три левых якоря и одно событие на каждой ноге внутри периода позиции;
это тест граничных условий, а не расписание реальной биржи.

Каждые ~250мс читается `/api/paper?state=all`: контролируются единственность
позиции, арифметическая согласованность итогов и отсутствие преждевременного
закрытия. Опрос статусов фиксирует ожидаемые blocked/partial, stale и восстановление.
Итог требует всех девяти наблюдений, отсутствия ошибок, одного opened/closed,
целых paper/market SQLite и совпадения результата с независимым расчётом.
В funding-логе должны быть минимум три прохода без сетевых запросов.

Файлы `metrics.json`, `*-status.json`, `*.log`, искусственные SQLite и снимок
остаются в выходной папке, в том числе при неуспехе. Ожидаемые blocked/partial
во время специально созданных сбоев не считаются ошибкой; отсутствие нужного
наблюдения завершает стенд с failed. Уменьшать штатный 60с период funding ради
проверки не требуется.

Этот стенд проверяет координацию процессов. Он не проверяет работу биржевых
адаптеров, закрепление REST-ног реальным монитором, естественный confirmed,
качество реальных settlement marks, суточную устойчивость или доходность.
Отдельная публичная проверка описана в [PAPER_LIVE_VALIDATION.md](PAPER_LIVE_VALIDATION.md).
