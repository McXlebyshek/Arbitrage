# Сборка в потоке и приоритет WS

Полная сборка использует снимок входных каталогов, оборота, котировок и
деталей. Рабочий поток обновляет свои кэши. После завершения event loop
принимает результат и маршруты. Подтверждено тестом замены каталога
во время подготовки и сохранения оригинальных источников для HTTP.

На 12 000 синтетических рынках проведён чередующийся контрольный замер:
21 пара запусков после пяти прогревов, таймер 5 мс. Медиана максимальной
задержки таймера внутри одного построения снизилась с 63,89 до 7,45 мс.
Медиана времени сборки составила 68,82 и 67,92 мс.
[Данные синтетического прогона](snapshot-worker-synthetic.json)

Живые окна по 100 секунд с общим WS-слоем имели p99 задержки event loop
49,04 и 59,82 мс, максимум 541,29 и 422,53 мс. Сводный p99 не улучшился.
В прогретых снимках диапазон времени сборки изменился с 57,3–345,4 до
64,5–79,3 мс. На обеих версиях отвечали все 14 источников из 14.
[До](ws-live-after.json) · [После](snapshot-worker-live-after.json)

Пара из реестра включается в приоритет WS. Из шести готовых живых снимков
PYBOBO трижды обслуживался синхронным WS и пропускал прямой REST. В одном
случае прямой стакан восстановил пару, когда WS её не покрывал. В двух
снимках синхронных котировок обеих ног не было. Для исключения REST нужно
подтвердить покрытие также на низколиквидных рынках и после обрывов.

Проверки. 61 Python-тест, 17 Node.js-тестов, Ruff и Playwright.
В браузере экранирование подтвердилось на повреждённом избранном и
на имени сети с HTML-разметкой.
