## Принудительное завершение процесса

Скрипт validate_crash_recovery.py использует **синтетические положительные сценарии**,
не рыночные данные. Дочерний процесс сохраняет confirmed-эпизод и вызывает os._exit(23),
минуя штатную остановку. Родитель получает освобождённую ОС-блокировку; отдельному
конкурирующему процессу с той же базой отказано (код 5). Новый запуск сохраняет ended
с причиной previous_session_interrupted и новым событием discovery-time; старый run
становится interrupted. Новое наблюдение имеет pending и счётчик 1. Штатная остановка
нового запуска оставляет stopped, integrity_check=ok.

Проверка повторена из G:\Arbitrage. Старое подтверждение не перенесено, повторного
recovery-события нет. Момент аварии не объявляется известным: termination_time_known=false.
Синтетический сценарий не смешивается с публичным архивом funding и живой базой.

Отдельный обычный публичный прогон с блокировкой: 62,23 с, шесть бирж, код завершения 0,
recent_failures пусты; monitor_runs в stopped. p95 публикации 41,51 мс. Это короткая
проверка нормальной записи/закрытия, не доказательство суточной устойчивости.

JSON-метрики и recovery-событие: `funding-recovery-summary.json`. Отчёт контролируемого
процесса из основной папки: `G:\Arbitrage\data\crash-recovery-report.json`.
Правила и источники протоколов: [FUNDING_RECOVERY.md](../FUNDING_RECOVERY.md).
