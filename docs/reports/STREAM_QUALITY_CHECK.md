# Диагностика Binance/Gate 0.34

Дата: 2026-11-05, Windows. Пользовательские процессы/базы не изменялись.
Прогоны использовали отдельные папки и loopback-порт 8776; реальные ордера и
внешние уведомления отсутствовали. Порог свежести 3с не менялся.

## Наблюдения и отвергнутая гипотеза

В исходных snapshots прогона 0.33 медиана `received_at_ms − source_timestamp_ms`
у Gate составила 4926,5мс, p95 19095мс. Это статистика сохранённых котировок с
повторениями, не измерение чистой сетевой задержки. Одного heartbeat недостаточно,
чтобы сделать такую котировку свежей.

Гипотеза о создании Task на каждый кадр через wait_for не подтвердилась:
в установленном Python 3.14 положительный timeout уже использует прямое ожидание.
Искусственное сравнение 50000 buffered receive показало 112,68/114,11мс для
wait_for и 105,14/102,62мс для inline timeout. Разница не доказывает причину
секундных задержек. Замена wait_for отменена; штатное чтение с таймаутом сохранено.
[Корректно подписанный benchmark](WS_RECEIVE_BENCHMARK.json).

Первый диагностический прототип (180с) подтвердил проблему: 270 API-ответов без
ошибок, но Binance переподключился 8 раз и принял 10384 уже устаревших обновления;
Gate — 3578. В прототипе использовался inline timeout, не оставленный в поставке.
Проблема не исчезла. [Метрики прототипа](STREAM_PROTOTYPE_METRICS.json).

## Одновременное сравнение размеров групп

Команда: `validate_stream_groups.py --output data/stream-groups-v034 --duration 90`.
Четыре независимых пула: Binance и Gate, по 20 или по 5 контрактов на соединение.
Одни публичные данные получались дважды; REST/SQLite-нагрузки монитора не было.
Метаданные взяты из сохранённого проверенного каталога. После прогрева 20с:

| Площадка / размер группы | Доля свежих в выборках | Переподключения | Принято устаревших обновлений |
|---|---|---|---|
| Binance / 20 | 10,36% | 5 | 7001 |
| Binance / 5 | 6,36% | 7 | 39517 |
| Gate / 20 | 0% | 0 | 10272 |
| Gate / 5 | 76,93% | 0 | 3336 |

Размеры окон и числа кадров различаются; счётчики нельзя трактовать как
нормализованные доли ошибок. Уменьшение группы улучшило Gate в этом коротком
сравнении, но не Binance. Это не доказательство конкретного серверного/сетевого
механизма. [Полные метрики](STREAM_GROUPS_METRICS.json).

## Изменения и проверка полного монитора

Добавлена настройка `--gate-group-size`, по умолчанию 5; фактический размер также
ограничен общим --group-size. Для текущих 20 активов Gate нужны 4 соединения.
Binance сохраняет прежнюю группировку: смена на 5 не показала улучшения.
Чтение отдаёт управление другим задачам каждые 256 накопленных кадров.
Добавлены ограниченные окна задержек источника/оболочки и счётчики stale/out-of-order,
сохранение счётчиков при замене групп и вывод в диагностический отчёт.

Полный монитор с Gate/5: `validate_paper_live.py --directory data/stream-gate5-v034
--duration 120 --port 8776 --rules`. Пять процессов, 126,67с, 183 ответа API без
ошибок, до 412 направлений, перезапуск трёх paper-workers на 62,03с, market SQLite
integrity_check=ok, архив после остановки и rules blocked.

После прогрева Gate: 94,66% свежих, 4 соединения, 0 переподключений и 0 принятых
уже устаревших обновлений. Binance: 6,55% свежих, 6 переподключений, 5257 устаревших
обновлений. Общий monitor_exit_code=1, качество неполное.
11 событий confirmed, но максимум сценария 0,434942 USDT ниже paper-порога 1;
paper-позиций нет. Живой положительный paper-цикл этим запуском не проверен.
[Метрики полного монитора](STREAM_GATE5_METRICS.json).

Это короткие окна. Gate не объявляется полностью исправленным, Binance остаётся
нерешённым. Новая телеметрия разделяет время источника и время оболочки, но ни одно
из них не подменяет исходный timestamp при допуске котировки.
Финальная поставка дополнительно прошла минутный запуск: 64,70с, 93 ответа API
без ошибок, целая market SQLite, перезапуск paper-workers и блокировка правил
после остановки. Качество рынка неполное, monitor_exit_code=1: Binance четыре раза
переподключился и принял 4374 устаревших обновления; Gate не загрузил каталог
из-за RequestTimeout, поэтому его WS-группы в этом коротком повторе не проверены.
Настройка групп не исправляет REST-timeout.
[Метрики установленной версии](STREAM_INSTALLED_METRICS.json).

В одном из сохранённых окон Binance p95 получения минус T = 8448мс,
получения минус E = 8447мс, E минус T = 1мс. Это указывает на задержку после
времени E в этом окне; вывод не отделяет передачу, буферы и локальную обработку
и не устанавливает причину закрытия сокета. Последнее окно после переподключения
снова короткое; p95 окон нельзя выдавать за статистику всей сессии.

Локальный WebSocket-тест передал 3000 устаревших кадров и один кадр с обратным
временем: цены не стали свежими, обратный кадр не заменил котировку, окно осталось
ограничено 2048 значениями. Проверены переподключение и сохранение счётчиков
после смены метаданных. Полная регрессия: 283 Python-теста / 11 JS-проверок.

Следующий шаг: сопоставить Binance T/E/локальное получение, задержки и закрытия
на нескольких временных окнах, отдельно диагностировать REST-timeout Gate.
Смена endpoint/heartbeat или ослабление свежести
без подтверждения причины не применялись.
