# Автоматическое обслуживание 0.13

По умолчанию во время работы monitor включён фоновый планировщик. Он не устанавливает
службу Windows или внешнее расписание: после остановки процесса работа прекращается.
Обычная публикация содержит блок `maintenance`, а актуальный итог планировщика записывается
в `<database>.maintenance.json`, включая stopped после завершения. Итоговый latest.json
может содержать более ранний снимок его состояния; проверять нужно время публикации.

| Настройка | По умолчанию |
|---|---:|
| Подробные снимки и закрытые эпизоды | 7 дней |
| Минутные сводки | 30 дней |
| Исторические события funding | 90 дней, минимум 31 |
| Период обслуживания при отсутствии остатка | 3600 секунд |
| Порция удаления | до 200 строк каждой таблицы |
| Управляемые архивы | до 3 файлов и 512 MiB суммарно |
| Период обновления долгой истории funding | 24 часа |

```powershell
# Обычный запуск: обслуживание включено
.\.venv\Scripts\python.exe -m arbitrage
# Полностью отключить фоновую очистку и автоматический импорт funding
.\.venv\Scripts\python.exe -m arbitrage --no-auto-maintenance
# Свои интервалы хранения и бюджет архивов
.\.venv\Scripts\python.exe -m arbitrage --raw-history-days 3 --summary-history-days 30 --funding-history-days 90 --backup-count 3 --backup-max-mib 512
# Оставить очистку, выключив только обновление funding
.\.venv\Scripts\python.exe -m arbitrage --funding-refresh-hours 0
```

raw-days > 0, summary-days >= raw-days, funding-days >= 31; backup-count 1–100,
backup-max-mib >= 1, maintenance-batch-rows 1–10000. maintenance-seconds >= 30;
funding-refresh-hours — 0 либо не меньше 1. Все числовые параметры конечные.

После прогрева 30 секунд отдельная задача проверяет импорт funding. Если все нужные
контракты уже импортированы без ошибок в пределах заданного периода, повторных запросов
не будет: cached_fresh относится к возрасту импорта, не к свежести текущей ставки или
полноте исторического окна. Иначе загружается архив 7/30 дней только для выбранных бирж
и зарегистрированных активов. После импорта/ошибки следующая попытка — через заданный
период; проверка свежего кэша повторяется не реже часа. Результаты обновления отображаются
в `maintenance.funding`, неполнота окон остаётся в таблицах истории.

## Порядок очистки

1. Проверяется checkpoint минутных сводок. Непосчитанная история откладывает удаление.
2. Выбирается ограниченная порция устаревших записей. Открытые эпизоды и эпизоды,
   пересекающие границу хранения, защищают подробные данные с прежним запасом 3 секунды.
   Сводки для защищённой старой истории также пока сохраняются.
3. Выбранные строки сохраняются в отдельный SQLite-архив формата retention_rows_v1,
   содержащий имена таблиц, исходные rowid, имена столбцов и точные значения строк.
   Это архив удаляемой порции, **не полная копия базы**. Он проверяется quick_check и
   числом записей до удаления источников. Неудача архивирования оставляет исходники.
4. Короткая транзакция снова проверяет защиту эпизодов. Удаляется строка, только если
   все её значения совпадают с сохранёнными. Новые события эпизода отменяют удаление
   всей группы; исправленная параллельным импортом ставка funding не теряется.
   Ошибка транзакции откатывает всю порцию; проверенный архив остаётся.
5. Если удалены строки, проверка остатка запускается через 5 секунд. Иначе действует
   обычный период. Очень большой эпизод, не помещающийся целиком в лимит, откладывается
   с batch_limit_blocked: можно увеличить лимит или применить ручное обслуживание.

Работа выполняется вне event loop. Ожидание SQLite-lock ограничено 50 мс, тяжёлые SQL
операции имеют бюджет около 100 мс: превышение даёт ошибку/повтор, а не ослабление защиты.
Это не гарантия нулевой задержки записи — публикация и очистка используют одну SQLite.
Для временных запросов добавлены индексы. При остановке монитор ждёт завершения уже
начатой порции и отменяет задачи импорта перед освобождением блокировки сессии.

## Ограничение архивов

Управляемый каталог — `data/managed-backups/<имя базы>-<идентификатор пути>/`.
Удаляются только проверенные файлы из его manifest.json с допустимыми именами и путями
внутри каталога. Посторонние/неучтённые файлы, ручные полные копии и папка версий backups
не затрагиваются и не входят в этот бюджет. Оставшийся после аварии неучтённый файл
показывается как unmanaged_files; автоматически он не удаляется.

Сначала удаляются более ранние управляемые архивы. Порядок добавления в manifest важнее
системных часов. Минимум один последний архив сохраняется. Если оператор понизил бюджет
ниже размера последнего уже существующего файла, он остаётся с budget_exceeded=true.
Новая порция, не помещающаяся в бюджет, не применяется: нужно увеличить бюджет либо
уменьшить maintenance-batch-rows. Бюджет не является ограничением всей папки проекта.

Архивы содержат ровно свои порции. После удаления старого архива соответствующие данные
больше не гарантируются к восстановлению: ограниченный бюджет — не бессрочное хранение.
Просмотр точных исходных значений без изменения архива:

```powershell
.\.venv\Scripts\python.exe -m arbitrage.history --archive 'data\managed-backups\...\backup-....sqlite3' --archive-table economics --limit 10
```

Онлайн-VACUUM не выполняется. Удалённые страницы SQLite используются новыми записями;
физический файл может остаться прежнего размера. Для уплотнения остановленной базы
сохранена ручная команда `arbitrage.maintenance --apply --compact` с полной копией.
Защищённые эпизоды, превышение бюджета, загруженная база или большая задержка backfill
могут удерживать старые данные. Это политика срока хранения с отчётом о препятствиях,
а не абсолютный предел размера активной базы. Суточная устойчивость проверяется отдельно.

Проверки: [AUTOCARE_CHECK.md](reports/AUTOCARE_CHECK.md).

## Графические сводки 0.15

Таблица `chart_rollups` хранит отдельные минутные цены/спреды и наблюдаемые ставки
для UI. Она подчиняется `--summary-history-days` и той же порционной политике архивов.
Если исходные сканы или снимки funding ещё не агрегированы, очистка возвращает
`aggregation_pending`, сохраняя исходные строки. UI сам базу не изменяет.
Для остановленной старой базы: `python -m arbitrage.chart_history --database data/market.sqlite3`.
Подробности: [UI.md](UI.md).
