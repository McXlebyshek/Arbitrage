В отчёте: изменения, проверки, следующий шаг и краткий общий план.Обязательный Git-checkpoint после завершённой порции работыПользователь хочет сравнивать версии через историю Git и видеть подробные комментарии к коммитам. Выполняй это автоматически в конце каждой завершённой и проверенной порции изменений, но не после каждой мелкой команды и не для задач без изменения файлов.1. Когда изменения и адресные тесты закончены, сначала обнови docs/ROADMAP.md (если этого требует задача), затем создай один осмысленный коммит для этой порции. Заголовок конкретный, тело коммита содержит «Изменения» и «Проверки» с результатами. Описывай именно сделанное, не заявляй о непроверенном.3. Делай checkpoint обычными командами Git из корня репозитория; отдельный скрипт не обязателен. Если .codex/tools/git_checkpoint.py реально существует, проверен и подходит для текущего состояния репозитория, его можно использовать. В любом случае добавляй только конкретные файлы этой порции (git add -- <пути>), проверь git diff --cached --check и git diff --cached, затем сделай один git commit с заголовком и подробным телом, после чего обычный git push в текущий настроенный upstream. Сначала проверь git rev-parse --abbrev-ref --symbolic-full-name @{upstream} (в PowerShell заключи @{upstream} в кавычки).4. Не используй git add ., git add -A без перечня файлов, git reset --hard, git clean -fd, git push --force, автоматическую настройку удалённого репозитория или push в другую ветку. Не коммить секреты, .env, логи, кэши, временные файлы, резервные копии. Если файл содержал изменения ещё до начала работы, не включай их в свой коммит: добавляй только собственные hunks (git add -p) после проверки либо пропусти Git-checkpoint и сообщи причину.5. Если Git не настроен, уже есть staged-правки, тесты провалены, нет upstream или push отклонён — не пытайся скрыть проблему. При чужих staged-правках не создавай коммит автоматически; при отсутствии upstream не пытайся создавать или выбирать удалённую ветку. Сообщи точную причину и что удалось сделать (например, «локальный коммит создан, push не прошёл»).6. В финальном отчёте укажи: ветку, короткий SHA, статус коммита и push, изменения, тесты, обновлённый краткий ROADMAP.
