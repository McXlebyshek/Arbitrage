# Работа над Arbitrage Monitor

## 1. Контекст проекта

Основная рабочая папка проекта — `G:\Arbitrage`.

`OLD` — архив предыдущего проекта для ознакомления. Рабочий код, зависимости, тесты и команды запуска текущего монитора размещать в основном проекте. Импорты и запуск из `OLD` запрещены.

Перед продолжением реализации обязательно прочитать:
- `docs/ROADMAP.md` — план и прогресс реализации.
- `README.md` — архитектура, требования и ограничения.

Текущий объём проекта — **monitor-only через публичные API**.

Реальные торговые операции, открытие позиций, управление ордерами и автоматическое исполнение сделок в MVP не входят.

Не расширять объём проекта без согласования с пользователем.

## 2. Работа с MCP

Использовать доступные MCP-инструменты, когда они помогают решить задачу точнее или эффективнее.

### Context7
- Использовать для проверки актуальной документации библиотек, API и фреймворков.
- Проверять совместимость методов с установленными версиями зависимостей.
- Особенно важно для CCXT, FastAPI, WebSocket и библиотек работы с криптобиржами.
- Не выдумывать методы, параметры и ответы API.

### GitHub MCP
- Использовать для работы с удалёнными репозиториями, Issues и Pull Requests.
- Перед изменениями изучать структуру и существующую реализацию.
- Не создавать PR, не выполнять push и не изменять удалённые репозитории без явного разрешения.

### Playwright MCP
- Использовать при разработке и тестировании веб-интерфейса.
- Проверять навигацию, формы, таблицы, фильтры и отображение ошибок.
- Проверять интерфейс после значительных изменений.
- Не считать UI протестированным без фактической проверки.

### OpenAI Developer Docs
- Использовать для задач, связанных с OpenAI API, Codex и официальными SDK.

### Общие правила MCP
- Не вызывать инструменты без необходимости.
- При отсутствии MCP использовать доступную альтернативу.
- Сообщать, если нужную проверку выполнить не удалось.
- Не утверждать, что инструмент использовался, если фактического вызова не было.

## 3. Правила разработки

- Перед изменениями изучать связанные модули.
- Сохранять существующую архитектуру, если нет обоснованной причины менять её.
- Предпочитать минимальные, точечные изменения.
- Не создавать дублирующий функционал.
- Не добавлять ненужные зависимости.
- Использовать типизацию Python, где это уместно.
- Обрабатывать ошибки API, таймауты и сетевые сбои.
- Не скрывать ошибки пустыми обработчиками исключений.
- Не изменять работающие компоненты без необходимости.
- Не удалять пользовательские данные и файлы без разрешения.

## 4. Особенности Arbitrage Monitor

- Использовать публичные API бирж.
- Учитывать ограничения частоты запросов (rate limits).
- Реализовывать безопасные повторные запросы при временных сетевых ошибках.
- Не создавать бесконечные циклы повторных запросов.
- Нормализовать символы и торговые пары между биржами.
- Проверять совместимость контрактов перед сравнением цен.
- Различать реальные данные API, тестовые значения и демонстрационные данные.
- Учитывать комиссии, ликвидность, спред и фандинг при расчётах.
- Не выдавать предполагаемую прибыль за гарантированную.
- Не добавлять торговые операции без явного изменения требований проекта.

## 5. Проверка изменений

После изменений выполнять доступные проверки:

1. Проверить синтаксис и импорты.
2. Запустить существующие автоматические тесты.
3. Использовать Ruff и pytest, если они установлены и применимы.
4. Проверить затронутые API-интеграции, когда это безопасно и возможно.
5. При изменениях UI использовать Playwright MCP.
6. Убедиться, что существующий функционал не нарушен.

Не заявлять об успешном прохождении тестов без их фактического запуска.

## 7. Отчёт после каждой порции работы

После каждой завершённой порции работы обновлять `docs/ROADMAP.md` и включать в итоговое сообщение:

### Что изменилось
Кратко перечислить фактически выполненные изменения.

### Проверки
Указать выполненные тесты, их результаты и оставшиеся ограничения.

### Общий план проекта
Повторить нумерованные этапы из `docs/ROADMAP.md`, используя статусы:
- ✅ Выполнено
- ◐ Частично
- ⬜ Предстоит

Не отмечать непроверенный или частично реализованный этап как полностью выполненный.

### Следующий шаг
Указать ближайшую задачу согласно ROADMAP.
