# Локальные уведомления 0.19

Монитор сохраняет локальный журнал подтверждённых **условных сценариев** и пишет
новые уведомления в свою консоль. Биржевые ключи, внешние сервисы и разрешение
браузерных уведомлений для этой версии не используются.

Отдельный просмотр: `Start-Alerts.cmd` из G:\Arbitrage.
Он сначала выводит сохранённый журнал с пометкой `saved_journal`, затем читает
новые записи раз в 2 секунды. Ctrl+C закрывает просмотр, не останавливая монитор.

```powershell
.\.venv\Scripts\python.exe -m arbitrage.alerts --database data/market.sqlite3 --limit 50
.\.venv\Scripts\python.exe -m arbitrage.alerts --database data/market.sqlite3 --watch
# Порог и подтверждения относятся к существующей условной модели:
.\.venv\Scripts\python.exe -m arbitrage --signal-min-usdt 1 --confirmations 3 --confirm-min-seconds 2 --alert-cooldown-seconds 60
# Отключить создание локальных уведомлений:
.\.venv\Scripts\python.exe -m arbitrage --no-local-alerts
```

`--signal-min-usdt` — строгий порог условного net, не сырого спреда.
Число подтверждений и интервал задаются существующим SignalTracker; каждое
подтверждение требует независимого обновления обеих ног. Уведомление дополнительно
сверяет текущий confirmed-эпизод, его количество подтверждений и net, время публикации
до 5с и исходные времена глубины до 3с (допуск будущего времени 1с).
Старая запись или повтор снимка не создаёт новое положительное уведомление.

## События и защита от повторов

- `opened`: свежий confirmed-сценарий, net строго выше порога.
- `closed`: условия ранее объявленного эпизода потеряны, серия сброшена,
  монитор остановлен или прежняя сессия восстановлена как прерванная.
- `suppressed`: внутренний аудит отклонённого уведомления; обычным просмотром не показывается.

Уникальный event ID защищает от повторной записи. Дополнительный confirmed того же
открытого эпизода не уведомляет повторно. Новый confirmed по той же связке ограничен
`--alert-cooldown-seconds` (по умолчанию 60с, допустимо 0–86400), включая новый запуск.
Подавленное cooldown событие не отправляется позже автоматически; нужно новое
подтверждение после смены условий. Для эпизода без записанного `opened` уведомление
о потере не создаётся. Потеря условий не ограничена cooldown.

Журнал сохраняется в `local_alerts` атомарно с исходными сигналами. Если запись
уведомлений не удалась, публикация сигналов также откатывается. Это защита целостности,
а не гарантия показа консоли ровно один раз: авария после commit до print может
пропустить консольную строку, но запись останется в журнале. При отключении опции
старые записи не удаляются; просмотр истории не подтверждает текущую пригодность связки.

Фоновое обслуживание хранит журнал по сроку сводок (по умолчанию 30 дней),
архивирует удаляемые строки порциями и сохраняет монотонность курсоров после очистки.
При выключенном обслуживании автоматической очистки нет. Открытый/защищённый исходный
эпизод может отложить очистку по общим правилам.

## API локального UI

`GET /api/alerts?limit=50&after_id=123` возвращает сохранённые видимые уведомления.
Без курсора — последние `limit` записей в порядке ID; с курсором — следующие записи.
Лимит 1–1000, курсор неотрицательный. Отсутствующая/старая база возвращает пустой список
без создания файла. Чтение read-only, изменения через HTTP не поддерживаются.
Элементы имеют классификацию `conditional_scenario_notice_not_execution`.

Визуальная панель, звук/браузерные уведомления и доставка Telegram пока не реализованы.
Telegram потребует отдельной настройки получателя; сейчас сообщения наружу не отправляются.
Событие `opened` не означает открытие реальной позиции, `closed` — её закрытие.
