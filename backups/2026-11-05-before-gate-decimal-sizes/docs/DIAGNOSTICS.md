# Диагностика запусков 0.5

WS-монитор записывает `data/run-report.json` при каждом сохранении снимка и при остановке.
Путь меняется через `--report`. Отчёт не содержит торговых ключей; проект работает на публичных API.

```powershell
# Пятиминутная проверка реестра с частым обновлением каталога
.\.venv\Scripts\python.exe -m arbitrage --duration 300 --interval 5 --top 0 --economics-pairs 0 --market-refresh-seconds 60 --report data\registered-report.json
# Профиль ALL: BBO-биржи в пределах 64 групп, глубина MEXC ограничена 40 книгами
.\.venv\Scripts\python.exe -m arbitrage --symbols ALL --max-connections 64 --mexc-depth-limit 40 --duration 240 --interval 10 --top 0 --economics-pairs 0 --report data\all-report.json
```

`duration` ограничивает рабочий цикл; после него требуется время для штатного закрытия соединений.
Для сравнения производительности запуски выполняются последовательно. Одновременные
процессы на том же компьютере могут влиять на измерения.

## Поля отчёта

- `finished`, `finish_reason`, `exit_code`, `shutdown_states`: завершение, причина и состояния после остановки.
- `observations`: число рабочих снимков; финальный stopped-снимок в эту статистику не включается.
- `elapsed_seconds`, `cpu_seconds`, `cpu_pct_one_core`: время и процессорное время данного процесса.
  Процент CPU рассчитан относительно одного ядра; это не процент загрузки всего компьютера.
- `peak_rss_bytes`, `last_rss_bytes`: наибольший наблюдённый и последний рабочий набор памяти Windows.
  Это значения в моменты снимков, а не непрерывный максимум ОС. Если измерение недоступно, записывается null.
- `rss_at_warmup_bytes`, `steady_cpu_pct_one_core`: базовая память и средний CPU после прогрева.
- `database_growth_bytes`: изменение размера файла SQLite за запуск. WAL/внешние файлы не учитываются;
  текущий модуль хранения использует обычный SQLite journal. Отчёт не оценивает срок хранения автоматически.
- `peak_publish_ms`, `publish_p95_ms_recent`: время расчёта, JSON/SQLite-записи и консольного вывода.
- `peak_loop_lag_ms`, `loop_lag_p95_ms_recent`: опоздание пробуждения после паузы цикла.
  Это показатель задержки event loop, а не измерение сетевой задержки биржи.
- `max_spread_rows`, `max_eligible_quotes`: максимум допущенных строк/котировок на одном снимке.

Перцентили используют последние 10 000 наблюдений. Общие максимумы и счётчики — за весь запуск.
Измерения RSS зависят от библиотек и прогрева: короткий прогон не доказывает отсутствие утечки памяти.

## Охват и ошибки

После `--report-warmup-seconds` (по умолчанию 60) для каждой биржи собираются:

- `steady_observations` и `steady_streaming_observations` — количество снимков после прогрева.
- `mean_sampled_fresh_fraction` — сумма свежих котировок / сумма выбранных рынков на этих снимках.
  Это доля по выборке снимков, не непрерывный uptime и не гарантия исполнения.
- `max_selected_markets`, `max_received_quotes`, `max_fresh_quotes`, `max_connections` — наблюдённый охват.
- `metadata_generation`, `metadata_failures`, `group_restarts` — обновления каталога и перезапуски по изменению контрактов.
- `reconnects`, `book_resyncs` — накопленные переподключения и REST-инициализации стаканов.
  Первая синхронизация MEXC входит в book_resyncs и сама по себе не является ошибкой.
- `recent_failures` — до 20 различных замеченных ошибок, включая уже восстановленные.

Счётчики сохраняются при замене группы и при остановке. Ошибка, после которой котировки
восстановились до следующего снимка, может не попасть в выборку состояний; накопленный счётчик
переподключений при этом сохраняется. Изменение ценовых ограничений и точности обновляет
метаданные без разрыва BBO. Канал пересоздаётся при изменении состава, идентичности или размера контракта.

`exit_code=1` по-прежнему означает неполный последний снимок, например stale или omitted_markets;
это отличается от необработанной ошибки выполнения. Проверять нужно вместе с finish_reason и статусами.
Пути JSON-снимка, отчёта и SQLite должны различаться; CLI запрещает их совпадение.


## Задержки WebSocket 0.34

Каждое connection_status содержит source_lag_samples, source_lag_p50_ms/p95_ms:
локальное получение минус исходный timestamp котировки. Окно до 2048 значений
очищается при новом соединении. Это суммарная задержка источника/передачи/обработки
с погрешностью часов, а не чистое сетевое время; отрицательные значения не обнуляются.
Счётчики received_stale_updates (>3000мс при получении) и out_of_order_updates
за жизнь worker суммируются пулом и переживают замену групп метаданных.

Для Binance отдельно читается E, для Gate time_ms: event_lag_p95_ms — получение
минус время оболочки; source_to_event_p95_ms — оболочка минус исходное время.
Они диагностические, не используются для обновления timestamp/допуска котировки.
У других каналов или при отсутствии времени поля null. Окна ограничены 2048
значениями; в run-report сохранены последние p95 отдельно по соединениям.
Это не общая p95 по бирже, не среднее/максимум всего запуска и не доказательство
причины задержки. Перед переподключением значения могут отражать предыдущую сессию.

Сравнение групп без нагрузки рыночной SQLite (новая папка, публичные WS):

```powershell
.\.venv\Scripts\python.exe validate_stream_groups.py --output data/stream-groups-001 --duration 90
```

Нужен сохранённый каталог docs/reports/REGISTRY_V033_CATALOG.json.
Данные Binance/Gate получаются дважды, для групп 20 и 5; после прогрева 20с
сравниваются доли свежих в выборках и счётчики. Проверка не редактирует базы,
не управляет пользовательскими процессами и закрывает свои группы в finally.

Искусственное сравнение обёрток ожидания без сети:

```powershell
.\.venv\Scripts\python.exe validate_ws_receive.py --output data/ws-receive-001.json
```

Оно не проверяет реальную сетевую очередь. В Python 3.14 положительный timeout
wait_for уже ожидает напрямую; наличие Task на кадр предполагать нельзя.
Результаты: [STREAM_QUALITY_CHECK.md](reports/STREAM_QUALITY_CHECK.md).


В 0.35 добавлен stale_stream_reconnects — число переподключений по отсутствию
пригодных котировок 30с при продолжающемся потоке. Это отдельная причина,
общий reconnects также учитывает переход после завершения закрытия сокета.
Счётчик срабатывает перед ожиданием ws_close; поэтому кратковременно он может
опережать общий счётчик переподключений. Никакие timestamps для этого не заменяются.


## Окна свежести 0.37

После остановки изолированного прогона можно прочитать сохранённые snapshots,
не изменяя SQLite. Нужны база и report одного прогона, новая JSON-выгрузка:

```powershell
.\.venv\Scripts\python.exe validate_freshness_windows.py --database data/binance-depth500-long-v037/market.sqlite3 --run-report data/binance-depth500-long-v037/monitor-report.json --output data/binance-depth500-long-v037/windows.json
```

По умолчанию окна по 60с, параметр --window-seconds допускает 1–3600.
Учитываются снимки после прогрева report.warmup_seconds, stopped исключён.
loading/reconnecting не исключаются. Для каждого окна сохраняются число/время
выборок, selected_sum/fresh_sum, доля streaming и две оценки свежести:

- fresh_fraction_of_selected: fresh_sum / selected_sum;
- fresh_fraction_of_peak_capacity: fresh_sum / (samples × наблюдавшийся максимум выбранных рынков биржи).

Вторая оценка не скрывает loading с нулевым selected, если позже в этом же
прогоне была известна ёмкость. Это наблюдавшийся максимум, не доказательство
полного охвата реестра; omitted и отсутствие metadata проверяются отдельно.
Пустая ёмкость даёт null, окна без выборок не синтезируются. Это выборки, не
непрерывный uptime и не время исполнения/прибыльности. Большие интервалы между
выборками не интерполируются.

complete_time_window показывает, что окно целиком расположено после прогрева
и до finished_at_ms. min_complete_window_fresh_fraction_of_peak_capacity не
учитывает обрезанную последнюю минуту; min_window... включает все наблюдённые
окна. Полное временное окно не означает непрерывность или равномерность выборок:
смотрите samples и first_sample_ms/last_sample_ms. Для незавершённого report
complete_time_window=false; используйте окончательный отчёт.

Неверные счётчики/максимумы вызывают отказ. Исходная база открывается mode=ro,
отсутствующий файл не создаётся, существующая выгрузка не перезаписывается.
Рекомендуется выполнять анализ после stop, чтобы чтение большого архива не
влияло на замер самого монитора.
