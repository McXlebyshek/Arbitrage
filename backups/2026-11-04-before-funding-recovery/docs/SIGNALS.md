# Подтверждения и жизненный цикл 0.10

Блок `signals` в JSON схемы 3 следует за расчётом `economics` и использует весь набор
кандидатов экономики, независимо от фильтра сырой таблицы. Если экономика выключена
(`--economics-pairs 0`) или используется REST-диагностика, `signals=null`.

Условие по умолчанию: полный `scenario_estimated` без причин блокировки и условный net
строго больше 0 USDT. Подтверждение требует минимум трёх наблюдений, в которых продвинулись
времена источников **обеих** ног, и не менее двух секунд между первым и последним
засчитанными наблюдениями. Повторная публикация тех же стаканов и обновление только одной
ноги не увеличивают счётчик. Накопить быстрые подтверждения, а потом просто подождать нельзя.

Сохраняются ограничения источников: возраст до 3 секунд, не более секунды в будущем,
расхождение ног до `--max-skew-ms`. Источник, движущийся назад, сбрасывает серию.
Остальные ограничения данных, глубины, размера, оборота и funding проверяет экономика.

Состояния текущего эпизода:

- `rejected`: неполный расчёт, не пройден порог net или контроль источников; причина сохраняется;
- `pending`: условия выполнены, но ещё недостаточно независимых подтверждений/времени;
- `confirmed`: выдержаны условия серии; **это подтверждённый условный сценарий**, не сделка;
- `ended`: кандидат вышел из проверки либо монитор остановлен; запись попадает в `ended` текущего снимка.

Потеря положительного результата или качества данных немедленно обнуляет серию.
При возвращении условий нужно накопить её заново. Разрыв между засчитанными стаканами
больше 10 секунд создаёт `continuity_reset`; одинаковое или уменьшающееся время публикации
закрывает эпизоды с причиной `publication_clock_not_advancing`.
Потеря WS-допуска закрывает эпизод как `quote_unavailable_or_ineligible`; при наличии
связки в допустимых WS-строках, но смене выбора глубины — `selection_changed`.
Точная диагностика исходных данных остаётся в снимках scanner/economics того же времени.

События: `appeared`, `qualifying`, `confirmed`, `lost`, `reason_changed`, `continuity_reset`,
`ended`. Событие содержит run ID, episode ID, pair ID, время, переход, причины, счётчик и
последнюю условную оценку. Повторяющееся состояние с теми же причинами не создаёт новое событие.
Новый запуск получает новый run ID и начинает подтверждения с нуля. История предыдущих
запусков сохраняется, подтверждения через перезапуск не переносятся.

```powershell
# Значения по умолчанию: 3 наблюдения, минимум 2 с, разрыв до 10 с, условный net > 0
.\.venv\Scripts\python.exe -m arbitrage --confirmations 3 --confirm-min-seconds 2 --confirm-max-gap-seconds 10 --signal-min-usdt 0
# Последние 100 событий, только чтение
.\.venv\Scripts\python.exe -m arbitrage.history --database data\market.sqlite3 --limit 100
# Последние события определённого направления
.\.venv\Scripts\python.exe -m arbitrage.history --database data\market.sqlite3 --pair 'bitcoin|okx:BTC-USDT-SWAP|mexc:BTC_USDT'
```

Параметры: confirmations 2–20, min-seconds от 0 до max-gap-seconds,
max-gap-seconds > 0, signal-min-usdt >= 0; все числа конечные. При редкой публикации
нужно явно подобрать допустимый разрыв, иначе серия безопасно начнётся заново.

Снимки `signal_snapshots` и события `signal_events` записываются в одной транзакции со
снимками котировок, scanner и economics. Уникальный event ID защищает события от повторной
вставки; индекс pair/time поддерживает запрос конкретной связки. Таблицы автоматически
добавляются в существующую базу без удаления старых данных. Команда истории использует
SQLite `mode=ro`, возвращает последние N событий в хронологическом порядке.
В памяти остаются только текущие кандидаты, закрытые эпизоды хранятся в SQLite.

`execution_verified=false`; реальные тарифы аккаунта и будущие ставки/глубина не подтверждены.
Уведомления не отправляются. В 0.11 добавлены минутные агрегаты и ручное управление сроком
хранения: [HISTORY_STORAGE.md](HISTORY_STORAGE.md). История funding 7/30 дней и
продолжение сессии после аварийного завершения ещё не реализованы. При аварии завершающего
события может не быть: время последнего снимка обязательно учитывать при чтении статуса.
